## Findings at the baseline

### S1 — P1: final failure state is captured before callbacks have drained

`src/adapter/windows.rs:206-209` flushes, stops admission, and captures `failed`
**before** `wl_close` waits for outstanding callbacks. `BlockAdapter::stop`
only sets an atomic flag; a callback that already passed the admission check can
still run. If that callback fails after the snapshot, `adapter.faulted()` becomes
true too late to affect `clean=true` or the successful process exit at lines
210-225. A late dispatcher error is similarly unavailable after the native
session is deleted.

Upstream confirms that the wait is the boundary: WinSpd
[`stgunit.c:252-280`](https://github.com/winfsp/winspd/blob/55c53bc454afbbba38bd1692f52beb77ed59142f/src/shared/stgunit.c#L252)
stores the dispatcher error at thread exit, while `SpdStorageUnitWaitDispatcher`
waits for that exit. Merely reading `wl_error` before shutdown is insufficient.

Required fix: preserve the final native dispatcher result before deletion and
evaluate sticky adapter/backend failures after callback drain. Distinguish the
expected cancellation from a deliberate shutdown from unexpected dispatcher
failure; preserve any failure already seen before shutdown.

Regression: deterministically delay a callback that entered before stop, allow
the close path to reach drain, then inject its write/flush failure. The result
must be `UNCLEAN_CLOSE`, `clean=false`, and nonzero exit. Repeat with an
unexpected dispatcher failure at drain and a normal cancellation control.

### S2 — P1: commit failures can be retried as a clean close after forced RO

`native/winspd_shim.c:203-217` reports one undifferentiated error from volume
lookup, lock, flush, and dismount. `src/adapter/windows.rs:191-196` treats all of
them as a retryable `CLOSE_BLOCKED`. It does not check whether the mounted
filesystem changed from RW to RO after publication.

This matters with the pinned consumer. WinBtrfs
[`do_write`, lines 8078-8092](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/flushthread.c#L8078)
sets `Vcb->readonly` after any failed commit, including filesystem-internal
failures that need not reach the bridge as a failed block request. Its
[`lock_volume`, lines 2288-2293](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/fsctl.c#L2288)
skips the commit when already readonly and can then return success. The volume
`FlushFileBuffers` path is a successful no-op in
[`btrfs.c:584-587`](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/btrfs.c#L584).

Consequently, an internal commit failure during the first Ctrl+C may produce
`CLOSE_BLOCKED`; a second Ctrl+C can skip the failed commit, dismount, and return
`clean=true` while the bridge's own fault flag stayed false. A background commit
failure before the first close has the same missing-state-check problem.

Required fix: distinguish a genuinely busy lock from errors in later close
phases and retain a permanent unclean result for failed commit/flush/dismount.
Recheck actual Btrfs RW state through the identified volume handle before and
after locking, so a forced-RO transition cannot become a clean RW close. Avoid
drive-letter lookup or reopening a path as the identity check.

Regression: inject each close-phase failure separately; only an open-file/busy
lock may resume normally. Inject an RW-to-RO state transition with no lower
block failure and confirm neither a first close nor a repeated close reports
success. Exercise filesystem-full/metadata-allocation failure in a disposable
image to check the real driver path where possible.

### S3 — P2: read/control panic catches do not immediately fault the session

`src/adapter/windows.rs:81-110` and `132-145` catch a panic and return generic
status 4, unlike the write callback at `112-130`, which also marks the session
faulted. In today's read/flush implementation a panic under the I/O mutex poisons
that mutex, so subsequent I/O or final flush discovers the problem. However,
`faulted()` still returns false until that next operation: an idle RW device
remains published after a callback panic. Future work outside the mutex would
also lose this indirect protection.

Required fix: make all valid-context callback panic paths immediately sticky,
and clear the read buffer on the panic return path as well. Continue to prevent
Rust unwinding across the C ABI.

Regression: trigger read, write, and control panics independently. Verify an
error response, immediate sticky state, zeroed failed-read output, rejection of
subsequent writes, and unclean close. A malformed/null callback input must still
be rejected without dereferencing it.

## Properties checked without a finding

- The C/Rust callback types and fixed ABI-size assertions match the pinned
  WinSpd interface. Synchronous callbacks return completed status with an error
  sense code when applicable; `TRUE` is not mistaken for I/O success.
- The boxed Rust context outlives native shutdown and dispatcher wait. There is
  no source-observed use-after-free in the current normal teardown ordering.
- Existing RW backing files use read/write access, Windows sharing mode zero,
  write-through, bounded in-place writes, and a successful `sync_all` before a
  block write is acknowledged. Invalid requests do not widen the payload range.
- One WinSpd dispatcher and the volume I/O mutex serialize operations. Partial
  writes continue from their returned byte count; write, backend-read, and flush
  errors are sticky, preventing successful later writes in that session.
- Session-specific serial matching avoids choosing a volume merely by drive
  letter. Lock handles remain held through device shutdown and callback drain.
- RW Unmap is rejected and its advertisement is disabled. CacheSupported is
  disabled; therefore testing only the C flush callback would miss the actual
  per-write flush path. Pinned WinSpd rejects SCSI SYNCHRONIZE CACHE when caching
  is disabled and forces FUA on dispatched reads/writes.

## Power-loss test boundaries and residual risks

The [Microsoft volume-lock contract](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ni-winioctl-fsctl_lock_volume)
includes flushing and the absence of open files. In the pinned WinBtrfs code the
lock's `do_write` performs the filesystem commit; the subsequent successful
volume `FlushFileBuffers` call does not independently prove it happened.
Application-level `FlushFileBuffers(file)` only invokes the driver's cache
flush path and is not, by itself, evidence of a committed Btrfs tree. Power-cut
tests must distinguish application write/flush completion, bridge block-write
acknowledgment, and a completed lock/dismount.

Run cuts before/within/after backing writes and flush, during filesystem updates,
during publication, and during close. Preserve a durable external record of
acknowledged operations before cutting the guest. Inspect a detached copy in
Linux before recovery, compare complete plaintext against the independent
expected acknowledged prefix where applicable, check both LUKS headers and all
keyslot bytes, and run read-only Btrfs checks. Partial or unacknowledged writes
must never be described as atomic transactions. Guest process termination,
guest power removal, backend I/O errors, and a host/physical-device power loss
are different fault models.

Remaining limitations include physical media/cache flush honesty, sub-sector
tearing and unacknowledged overwrite damage, consumer-driver internal error
reporting, hangs in synchronous Windows storage calls, and arbitrary third-party
kernel-driver behavior. Source review and a finite VM matrix do not prove these
away. The existing experimental virtual-image scope and ext4 publication gate
remain appropriate.

## Disposition

Baseline recommendation: **do not release v0.3.1 as remediated while S1 or S2 is
open**. S3 should be fixed in the same fault-handling pass. The implementation
agent received all three findings before this report was written. A follow-up
section will record reviewed fixes and their evidence; this baseline review does
not certify work that has not yet been inspected.

## Release assessment for application flush durability

The missing Btrfs transaction commit on `FlushFileBuffers(file)` is **not fixed**
by these bridge changes. A successful application write, `FlushFileBuffers`, or
`FileStream.Flush(true)` must not be advertised as a durable filesystem checkpoint
in the supported WinBtrfs v1.10 stack. It is distinct from the bridge's guarantee
that each successful block-write callback has completed its backing-file flush.

This limitation does not by itself prevent an explicitly experimental v0.3.1
patch release with a narrow contract: **orderly bridge close, including successful
volume lock/commit and dismount, is the supported filesystem commit boundary**.
The limitation should be visible beside RW usage and in the release notes, not
only in this review report. Applications that depend on fsync/FlushFileBuffers
for crash recovery, such as databases, are outside that contract. Any claim of
general application-level crash durability remains blocked.

The test record must compare a cut immediately after application flush with a
cut after successful orderly close, using fresh disposable images and an external
expected manifest. An application-flush result that loses the update is a
documented **unsupported/failed durability observation**, never a durability PASS.
A run that happens to preserve the update does not establish the missing
guarantee because the background commit timer may have run. Conversely, loss of
data promised at a supported completed-close boundary, or loss of acknowledged
block data outside the explicitly unacknowledged/torn-write range, is a release
blocker even for this experimental contract.

At this follow-up review, VM execution and publication are still the implementation
agent's responsibility. This report provides source-level remediation findings
and a bounded release judgment, not an unconditional audit certificate.

## Native regression harness added by the reviewer

The reviewer subsequently added [`native/tests/close.c`](../../native/tests/close.c),
a standalone Windows test translation unit that includes the real
`native/winspd_shim.c`. Win32 volume/mutex operations and all invoked WinSpd
functions are substituted after the platform headers have been parsed. The
production implementation is not copied into a second model, altered, or linked
against a test-specific production build.

Its 25 deterministic cases cover:

- Six final dispatcher-result cases: success, expected late cancellation,
  unexpected late I/O/handle errors, a prior failure followed by cancellation,
  and a prior cancellation that must not be normalized. The assertions require
  before-status, shutdown, wait, after-status, deletion, and handle release in
  that order, preserving the locked volume until after unit deletion.
- Fourteen close cases: four busy/sharing lock results, a non-busy lock I/O
  error, RO before lock, RO after failed or successful lock, mode-query failures,
  flush and dismount failures using the same error code as a busy lock, a foreign
  serial, and successful/idempotent lock retention through teardown. These test
  both the returned phase and which later operations were prevented.
- Five publication cases: existing global guard, denied guard creation, failed
  unit creation, failed dispatcher startup, and successful publication/teardown.
  An existing guard must prevent any call to the WinSpd creation boundary.

The harness uses only process-local allocation and error state outside its
mocks. It never opens a real volume, creates a real named mutex, invokes a real
WinSpd unit, or changes drivers/services/registry policy. No WinSpd import library
or installed driver is needed. In the x64 MSVC CI shell, after preparing the
same pinned SDK, build and execute it with:

```powershell
cl /nologo /W4 /I "$env:WINSPD_SDK/inc" native/tests/close.c /Fe:native-close-test.exe /link advapi32.lib ole32.lib
if ($LASTEXITCODE) { throw 'Native close test build failed' }
./native-close-test.exe
if ($LASTEXITCODE) { throw 'Native close tests failed' }
```

Execution was verified by the reviewer in
[CI run 34749762390](https://github.com/DPS0340/winluks/actions/runs/34749762390),
for commit `d4f670a2e67240b62dea86dccc5f44f5fdd5618b`. The Windows MSVC job
compiled the harness and printed `native lifecycle tests: 25 cases passed`.
Both platform jobs passed all 37 Rust tests; the Windows job used
`--features winspd,vendored-openssl` and its log explicitly shows the callback
panic and post-drain failure tests passing. The reviewer checked the run's
commit, successful job conclusions, and test output, rather than inferring
execution from the presence of the tests in source.

The native phase failures and RO transitions are **mocked OS-result tests**.
They validate the shim's response to supplied results, not whether WinBtrfs
really emits those results or whether a physical storage stack honors flushes.
The real-VM fault matrix and application-flush limitation remain separate.

## Additional real-VM evidence — failure and acknowledgment boundaries

The reviewer subsequently read the controller reports, event records, Linux
verifier results, and relevant console output for `full-01`,
`power-flushed-01`, `power-flushed-02`, `process-flushed-01`, and `raw-04`.
All report the same candidate executable SHA-256 as `normal-03`. The reviewer
also inspected the controller, Windows workload, and Linux verification code
that establish the acknowledgment/cut order. No VM was operated by the reviewer.

**S2 now has real filesystem-full evidence beyond the mocked phase tests.**
In `full-01`, the Btrfs workload reported 221 successful file-flush events and
then `HRESULT 0x80070070` (`ERROR_DISK_FULL`, 112). On close, the production
bridge printed `CLOSE_FAILED phase=0 code=19`, then `clean=false` and
`UNCLEAN_CLOSE`, and its separately observed process exit was 1. This exercises
the actual forced-RO mode guard: the failed filesystem state is not converted
into a retryable busy close or a successful shutdown. The old canonical files,
LUKS header region, image length, and a read-only Btrfs check were preserved;
none of the 221 new files survived. This is a **passed failure-reporting check**
and a **failed application-flush durability observation**, not successful
persistence of those new files. It fills the virtual Btrfs filesystem; it does
not exercise an out-of-space backing NTFS filesystem or physical host disk.

The missing application-flush durability is also **observed, not merely inferred
from source**:

| Trial | Trigger after four successful file flushes | New files preserved | Structural/baseline checks |
| --- | --- | --- | --- |
| `power-flushed-01` | Kill the disposable QEMU process | 0/4 | Btrfs check 0; canonical files, header region, and image length unchanged |
| `power-flushed-02` | Repeat with a fresh disposable guest | 0/4 | Same checks passed |
| `process-flushed-01` | Force-terminate the publisher, confirm device removal, then cut the guest for extraction | 0/4 | Same checks passed |

The Windows workload explicitly used `FileOptions.WriteThrough` and
`FileStream.Flush(true)` before emitting each of these host-observed events.
Their successful return did not commit the Btrfs file tree. The JSON field
`required_checks_passed=true` in these trials means the selected structural and
canonical-data checks passed; it **must not be summarized as file-flush
durability passing**. Together with `normal-03` preserving 4/4 files after a
completed close, these results support the narrow commit-boundary distinction
and the exclusion of applications requiring fsync-style crash recovery.

**`raw-04` passed the acknowledged block-write durability check.** The workload
first locked and dismounted Btrfs, then captured a complete 240 MiB plaintext
baseline before the tested writes. The host copied that baseline over SSH and
verified its length/hash before sending the go signal. The reviewer separately
hashed the stored baseline and confirmed
`ef9843b5e80b39e440f2c7775ee236fd04c987651ec191ce120b15e58e654768`.
The exact observed writes were `(offset=0, length=512, seed=83)`,
`(131072, 1048576, 112)`, and `(251657728, 512, 141)`, each followed by a
successful raw-device flush and an event delivered to the host. The workload
kept the lock and raw handle open; the controller verified it was still alive
when sending SIGKILL to the specific trial QEMU process.

The Linux oracle decrypted the unbooted detached image with dm-crypt and compared
all **251,658,240 bytes** against that pre-write baseline plus the independently
specified byte patterns. The complete comparison passed, as did unchanged LUKS
header/keyslot region, canonical fixture, and image size. The baseline includes
the filesystem metadata committed by the prior lock; it is not reconstructed
from the post-cut image. This tests survival after acknowledged raw block writes.
It does not establish atomicity of a cut during an unacknowledged write, run a
Btrfs filesystem check on the deliberately overwritten raw payload, or simulate
physical host power loss.

No new storage-source blocker was identified by this evidence. The experimental
release judgment remains conditional on reporting the demonstrated file-flush
limitation prominently and keeping the final fault-matrix totals separate by
guarantee; the remaining trials were still underway at this checkpoint.

## Final review conclusion

The final review covered
[`docs/evidence/v0.3.1-powercut.json`](../evidence/v0.3.1-powercut.json),
[`docs/POWERLOSS-v0.3.1.md`](../POWERLOSS-v0.3.1.md),
[`README.md`](../../README.md), [`docs/VALIDATION.md`](../VALIDATION.md), and
the final candidate RO result in the lifecycle evidence. The reviewer checked
all 20 public trial rows against their original controller, event, and Linux
verification records, including every published event/report SHA-256. All values
and hashes matched. The four recorded reproduction-script hashes matched the
reviewed scripts, and all three frozen backing-chain files retained the recorded
sizes and modification timestamps.

There are exactly ten case types with two unique final trials each. The five
retained preliminary/incomplete/oracle-failure attempts are disjoint from those
20 trials and have explicit exclusion reasons; the failed preliminary full raw
comparison is preserved rather than counted as a pass. The source of the raw
prewrite baseline and the non-deterministic timing of streaming/close cuts are
accurately described in the public report.

| Guarantee or observation | Independently checked final result |
| --- | --- |
| Filesystem/canonical-data integrity after the listed virtual failures | 18/18 filesystem trials: read-only Btrfs check and mount passed, canonical files survived, mirrors agreed, and header/keyslot bytes and image length were unchanged |
| Acknowledged raw block writes followed by guest hard cut | 2/2 raw trials: three writes each, with every byte of each 240 MiB payload compared to the authenticated prewrite state plus expected changes |
| Completed orderly close followed by hard cut | 2/2 trials, all eight new files across the two trials preserved; actual close exit 0 and `clean=true` |
| Dedicated application-flush then abrupt-termination trials | **Durability failed in all four trials: 0/4 new files retained per trial**; structural-check success does not change that judgment |
| Actual Btrfs ENOSPC/forced-RO close handling | 2/2 trials returned the correct failed-close phase/error, `UNCLEAN_CLOSE`, actual exit 1, and `clean=false`; new uncommitted files were lost |
| Final candidate default RO and ext4 gate | Six original files matched; disk/volume RO flags set; create/rename/delete/raw-write attempts rejected; complete image hash unchanged; device removed after actual exit 0 and clean close; ext4 blocked before password input |

The final RO result identifies the same `d4f670a` candidate executable hash as
the fault matrix. The reviewer also verified that the production Rust sources,
native shim, Cargo application inputs, build script, and CI workflow had no
changes from that tested candidate at this checkpoint. The small later native
test casts, reports, packaging, and documentation do not alter its application
behavior. Final packaging/CI and publication remain the implementation agent's
responsibility.

One documentation accuracy issue found in the final pass was corrected: the
v0.3.1 README no longer implies that the historical Windows RW reopen and
Linux-to-Windows return-file tests were repeated in this run. The current
v0.3.1 lifecycle evidence has eight-file Windows-to-Linux verification and a
six-file candidate RO regression; earlier v0.3 results remain separately labeled.

**No unresolved storage-source or result-classification blocker was found for
the published experimental prerelease contract.** S1 and S3 have source and
regression-test evidence, while S2 additionally has the actual ENOSPC/forced-RO
failure path. The README and release guide place the observed application-flush
failure beside RW usage, exclude fsync-dependent applications, and state the
normal lock/dismount close boundary. The public report does not combine integrity
passes with application durability failures into an overall durability PASS.

This conclusion applies to the reviewed hash-identified binary, restricted
virtual-image/filesystem profile, and listed observed triggers. It does not
approve general application crash durability, physical host/controller power
loss, deterministic sector tearing, untested native/kernel behavior, or an
external human/cryptographic audit. Those limits remain open and explicitly
documented; the earlier pending-matrix checkpoints above are historical.
