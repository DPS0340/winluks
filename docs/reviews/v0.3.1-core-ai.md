## CORE-01 — validate Btrfs mirrors before publication (P1)

**Baseline evidence:** `src/probe.rs:18-25` reads only the primary superblock at 64 KiB.
`UnlockedVolume::validate` (`src/volume.rs:103-108`) trusts that result before creating a
`ValidatedVolume`. The pinned WinBtrfs v1.10 consumer instead reads every in-range mirror
and selects the greatest generation whose checksum is valid. Its addresses are 64 KiB,
64 MiB, and 256 GiB. Thus a clean primary does not establish the profile of the superblock
the consumer will actually use.

A newer valid-checksum mirror can contain an outstanding log tree or a different feature
profile. The bridge accepts the primary, then exposes a filesystem state that bypassed its
recovery/feature gate. Divergence is particularly relevant after an interrupted superblock
write; the issue does not require changing the LUKS metadata or defeating its password check.

Sources inspected at pinned WinBtrfs commit
`a0648190b4b238ebc016ce247d91ccc814a8633b`:

- [Mirror locations](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/btrfs.h#L14).
- [Highest-generation selection](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/btrfs.c#L2919-L2949).
- [Per-mirror writes](https://github.com/maharmstone/btrfs/blob/a0648190b4b238ebc016ce247d91ccc814a8633b/src/flushthread.c#L2327-L2335)
  copy one superblock and one device item, changing only the address and checksum.
- Linux v6.12 likewise changes only those two fields in its per-device
  [mirror write loop](https://github.com/torvalds/linux/blob/v6.12/fs/btrfs/disk-io.c#L3506-L3544).
  Its source also explains that non-primary mirrors can briefly retain an older version.

**Executed reproduction:** a standalone harness compiled the baseline `src/probe.rs`, used
its actual publication entry point, and supplied the committed Linux-generated primary plus
a checksum-correct 64 MiB mirror. The newer mirror had generation 10 and `log_root=4096`;
the primary had generation 9. The baseline result was `Ok(())`, with exactly one read at
65536. No filesystem was mounted and no image was modified.

Four regression tests were added to [tests/probes.rs](../../tests/probes.rs). They include
the actual source module to exercise its crate-private publication function without adding
a public API or copying the probe algorithm. All four failed on the baseline as expected:

| Test | Baseline observation |
| --- | --- |
| `btrfs_publication_checks_every_available_mirror` | Read only 64 KiB; ignored 64 MiB mirror |
| `btrfs_publication_rejects_newer_mirror_with_log_tree` | Accepted the newer recovery-state mirror |
| `btrfs_publication_rejects_divergent_mirrors` | Accepted different filesystem identity |
| `btrfs_publication_rejects_damaged_or_unreadable_mirrors` | Accepted damaged mirror |

The tests also cover the 256 GiB mirror through bounded virtual reads; they do not allocate
a 256 GiB image.

**Required correction:** read and validate every in-range mirror before publication, validate
each recorded address, and fail closed on checksum/profile or generation/identity disagreement.
A conservative supported profile can require equality after excluding only the checksum and
mirror address. This intentionally rejects states that Linux might be able to recover; it
must not silently select a backup or replay a log. Real clean Linux and WinBtrfs fixtures must
continue to pass that comparison. Re-review status is recorded below when the fix is ready.

## Other observations and test coverage

- Both LUKS2 headers must independently validate and agree; unknown operational JSON fields,
  duplicate keys, invalid numeric strings, overlapping keyslot areas, unsupported profiles,
  and reencryption requirements are rejected. Selected slots are bound through a digest to
  the supported segment; a recognizable filesystem does not replace the key digest.
- Payload reads, writes, and flushes share a mutex. Offset calculations are checked; writes
  require 512-byte alignment, stay within the fixed payload, and flush before success.
  Backend write/flush failure and RW backend read failure persistently fault the session.
- XTS treats each 512-byte sector as a separate data unit. Keyslot encryption key length is
  independent of volume-key length. The established 30-case Linux differential evidence is
  much stronger than encryption/decryption roundtrip tests alone, but was not independently
  rerun by this reviewer.
- Volume keys, AF/KDF buffers, Argon2 memory, and intermediate plaintext use explicit
  zeroization; the long-lived volume key attempts page locking. The soft KDF deadline is
  checked after a bounded computation, consistent with the documented soft-deadline policy.
- A possible close-result race was forwarded to the Windows reviewer: the baseline samples
  the fault state before native callback drain. Its disposition belongs to that lifecycle
  review and must not be inferred from successful crypto tests.
- Simultaneously publishing distinct copies with identical Btrfs filesystem/device UUIDs
  needs a consumer-level decision. Exclusive backing-file handles do not establish unique
  filesystem identity across different files. This was forwarded to Windows review; this
  core pass did not execute simultaneous-clone VM tests.

## Limits

The superblock/profile gate is not a complete Btrfs consistency checker, nor authentication
of hostile filesystem metadata. AES-XTS does not provide ciphertext integrity. Filesystem
trees and external kernel drivers remain additional trust boundaries. This review did not
audit OpenSSL/Argon2 internals or external driver implementations in full, prove zeroization
under process termination, or measure resistance to side channels. Unix file locking is
advisory and does not exclude uncooperative writers. File flush completion cannot establish
that physical storage honors its persistence contract.

Power-cut experiments, injected backend faults, final Windows lifecycle validation, and
release evidence are tracked separately. Their success must be assessed against the explicit
failure model and exact release build; this source review does not certify all possible
power-loss timings or physical hardware.

The harness creates a new QCOW2 overlay from a prepared powered-off base, confirms that
its recorded QEMU PID references that trial disk, and kills that QEMU process. It then
attaches the unbooted disk read-only to the Linux oracle. Extraction uses a read-only NTFS

`btrfs check --readonly` and a `ro,nologreplay` mount. This ordering avoids contaminating the
crash evidence with a Windows reboot, NTFS repair, or Btrfs replay before the oracle.

The initial harness had four evidence-quality problems that were reported and corrected:

1. It could stop reading workload events when the child exited, without parsing remaining
   output. The updated version drains stdout and reparses the complete captured worklog.
2. An empty expected-record list could satisfy `all([])` in the normal-close oracle.
   Completed workloads now require four file observations and a completion event; the
   normal-close verifier independently requires those records. Stream cases require an
   observed write event before they can be counted.
3. Normal-close captured the process exit and clean-close marker without enforcing them.
   The updated harness requires exit zero and `clean=true` before that case is accepted.
4. Any failure could previously count as disk-full. The workload now reports its innermost
   HRESULT, and the runner requires a nonzero exit with confirmed `ERROR_DISK_FULL`.

The corrected scripts are adequate for their explicitly bounded, supervised VM experiments;
these interpretation limits are required:

- `power-stream` cuts after the first observed file-write event. `power-close` cuts after
  the close request. Neither trigger proves that a particular storage callback or
  lock/flush/dismount phase was active at the instant of the cut.
- SIGKILL with the configured QEMU `cache=none` removes the running guest/hypervisor process.
  The host kernel and storage remain powered, and already-issued host I/O can complete.
  This is not a physical host/controller/device power-loss test or a deterministic
  torn-sector test.
- A Windows file-write or `Flush(true)` event is an application/API observation, not evidence
  that WinBtrfs has committed its transaction or that a particular block callback completed.
  In this pinned consumer, application flushes must not be represented as guaranteed
  file durability. Missing observed records are a failed/unsupported application-durability
  result even if the old canonical files and filesystem consistency survive.
- `required_checks_passed` for crash cases checks retained canonical files and filesystem
  consistency; only normal-close requires all four new records. It must not be presented
  as a blanket power-loss/durability pass. The separate record-presence/hash results are
  essential evidence, including loss and mismatch outcomes.
- The disk-full workload fills the Btrfs filesystem inside the fixed-size image. It does
  not demonstrate exhaustion of NTFS, the Linux host filesystem, or the physical storage
  backend. Backend error injection covers a separate failure boundary.
- Interrupted harness runs can leave a fresh trial VM or read-only oracle attachment for
  supervised cleanup. Extraction/mount errors before a result file is created are failed
  or incomplete trials. The final matrix must account for them rather than silently omit
  them; a crash disk must not be booted to obtain a cleaner result.

The source pass does not approve or reject runtime outcomes that were still being gathered.
Final evidence must identify the tested executable and retain the distinction between
filesystem consistency, application record persistence, clean close, and block-level
persistence. A direct block-write acknowledgement oracle is needed for a runtime claim about
the bridge's acknowledged-block durability; these filesystem events do not establish it.


## Direct block acknowledgement and outer-container follow-up

Reviewed the subsequent raw-workload additions in `scripts/windows/powercut-raw.ps1`
and `--block-oracle` in `scripts/linux/verify-powercut.py`, plus the revised extraction
and process-exit observation paths. This remained a source/read-only evidence review.

The raw client locks and dismounts the filesystem, keeps its volume handle, and opens the
WinSpd physical-disk handle with `FILE_FLAG_NO_BUFFERING | FILE_FLAG_WRITE_THROUGH`.
Page-aligned memory backs aligned first-sector, 1 MiB, and last-sector writes. An event
is emitted only after `WriteFile` returns the requested byte count and `FlushFileBuffers`
succeeds. These are block-device API acknowledgements and are distinct from the earlier
file-level flush observations. The Linux path reconstructs expected changed bytes using
an independent implementation of the specified pattern and compares the complete plaintext.
The intentionally overwritten raw image must not be treated as a valid filesystem fixture.

Three issues were raised for correction before counting this raw test as passing evidence:

- The subprocess reader combined `select()` on an OS descriptor with Python's buffered
  `readline()`. It can prefetch the final event into the Python buffer, then wait for the
  descriptor to become readable again while the raw client sleeps. In that case, the
  harness can miss the held-handle window and only cut after the client releases the
  filesystem. A local sleeping-producer reproduction confirmed an unread complete line
  in the Python buffer while `select()` reported no descriptor data. Use an unbuffered
  pipe or an explicit byte/line reader, and reject a raw workload that has already exited
  before the selected cut point.
- The raw oracle originally verified the canonical ciphertext hash but not the reference
  plaintext hash and size. It must anchor both before using the plaintext as expected
  data; a stale or accidentally replaced reference is not an independent oracle.
- Counting any three `block-flushed` events is insufficient to establish the claimed
  coverage. Validate the exact expected `(offset, length, seed)` tuples, including
  alignment, bounds, uniqueness, and the last-sector location derived from the validated
  plaintext size. Malformed, duplicate, or empty writes must fail the test.

A separate potential false-negative was noted: RW mounting and dismounting can commit
legitimate filesystem metadata before the raw writes. If that happens, comparison with
only the original canonical plaintext plus raw changes must fail. The remedy is an exact,
verified baseline taken after that preparation, not broad exclusion of metadata differences.

The extraction code now asks `lsblk --tree` to retain partition hierarchy. For the prepared
Windows evaluation guest's BitLocker outer partition, `dislocker -r -c` uses the existing
clear key with a read-only mapping. The option meanings were checked against
[Dislocker's primary source](https://github.com/Aorimn/dislocker/blob/master/src/config.c).
The raw disk, clear-key mapping, NTFS mount, and LUKS mapping all remain read-only during
extraction; the Windows crash disk is not rebooted. This does not add recovery credentials
or change encryption state.

Read-only inspection of the actual `normal-03` reports confirmed executable SHA256
`e4c66309d46c6bf6e6f8c73630596f3e426472704050cc531a22202b1405d0b8`, an independently observed
publisher exit code of zero, `clean=true`, and four distinct nonempty file-flush events.
All four files persisted; the Linux oracle reported unchanged canonical files and LUKS
header, successful filesystem check, and agreeing generation-10 mirrors. The reviewer

This supports normal-close persistence followed by a guest hard cut. It does not establish
pre-close file-flush durability. A separate PowerShell process object opens the publisher's
handle before close and observes its real exit code; SSH/ConPTY exit status alone is not
used as that evidence.

**resolved**: workload stdout is unbuffered; the raw client holds its handles indefinitely

No metadata ranges are ignored. This separates preparatory filesystem commits from the

The prepared base must not contain a stale go-file; the reviewed trials use fresh overlays.
